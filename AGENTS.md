# SpeakText contributor instructions

These instructions apply to the entire repository.

## Product constraints

- Target Fedora 44 Workstation, GNOME 50, and Wayland. Do not add X11, KDE,
  Windows, macOS, RPM, or Flatpak support unless the task explicitly requires
  it.
- Keep transcription fully local. Network access is allowed only for fetching
  pinned build sources and downloading the verified Whisper model.
- Never persist microphone PCM, transcripts, clipboard contents, or dictated
  text in files, logs, telemetry, crash reports, or test artefacts.
- Use XDG Global Shortcuts and Remote Desktop portals. Do not bypass Wayland
  security with `ydotool`, `uinput`, compositor extensions, accessibility
  scraping, or global keyboard hooks.
- Request keyboard access only. Do not request screen, pointer, or touchscreen
  access.
- Preserve the documented insertion rule: text goes to the cursor focused when
  transcription finishes. Never claim that the original focus can be restored
  or verified on Wayland.

## Architecture boundaries

- Keep GTK and portal orchestration in `src/speaktext`; the C++ worker must
  remain UI- and portal-independent.
- Keep `extension/` limited to a GNOME top-bar indicator and non-sensitive
  controls. It must not access the microphone, portals, worker, clipboard, or
  transcript text. The D-Bus control interface may expose only state labels,
  content-free status messages, and whether recovery text can be copied.
- `DictationCoordinator` is the sole owner of dictation state transitions.
- `AudioCapture` must stream PCM through pipes or memory and must not create a
  temporary audio file.
- Keep one persistent `TranscriptionWorker` process so the model is loaded once.
- Maintain the documented little-endian, length-prefixed worker protocol. If it
  changes, update both implementations, tests, and `docs/architecture.md`.
- If the top-bar D-Bus interface changes, update the Python service, Shell
  extension, tests, and `docs/top-bar.md` together.
- Preflight the complete transcript before keyboard insertion. Do not retry a
  partial insertion automatically because that can duplicate text.
- Keep clipboard fallback explicit and recoverable. Retain failed text only in
  process memory and clear it after copying, replacement, or exit.

## Development style

- Use Australian English in documentation, messages, comments, and UI copy.
- Prefer the Python standard library and installed PyGObject APIs. Avoid adding
  Python packages unless there is a clear requirement.
- Keep asynchronous microphone, worker, and model operations off blocking GTK
  paths. Never perform expensive work in a portal signal callback.
- Handle failures explicitly and return the coordinator to a usable state after
  runtime errors.
- Diagnostic logging may contain state names, timings, byte counts, paths, and
  error categories, but never transcript or PCM content.
- Preserve unrelated work and avoid broad refactors when making focused fixes.

## Commands and verification

- Check Fedora dependencies without modifying the system:

  ```bash
  ./scripts/bootstrap.sh --check
  ```

- Build the pinned CPU-only worker:

  ```bash
  make build
  ```

- Run the automated suite:

  ```bash
  make test
  ```

- Run the optional real-model worker integration test only when a verified
  model is already available:

  ```bash
  SPEAKTEXT_TEST_MODEL=/path/to/ggml-base.en.bin \
    PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src \
    python3 -m unittest tests.test_native_worker -v
  ```

- For portal, microphone, and cursor changes, also follow
  `docs/acceptance-testing.md`. These checks require an attended GNOME session
  and must not be launched unexpectedly during automated verification.
- Do not run installation scripts against the user's real home merely to test
  them. Use an isolated temporary `HOME` and `XDG_DATA_HOME`.
- Do not commit `build/`, `third_party/`, model files, PCM fixtures derived from
  user recordings, logs, permission restore tokens, or generated bytecode.

## Documentation requirements

- Update nearby documentation when behaviour, commands, permissions, paths,
  protocol framing, privacy guarantees, or supported platforms change.
- Keep `README.md` concise and user-facing. Put detailed design and maintenance
  material under `docs/` and link it from `docs/README.md`.
